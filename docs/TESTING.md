# Чеклист ручного тестирования TON Site Builder

Документ для приёмки. Автотесты покрывают логику (41 тест backend, 17 фронта) и
сквозной сценарий (63 проверки по живому стеку) — здесь то, что проверяется руками:
интерфейс, кошелёк, реальные транзакции и Telegram.

Отметки: ✅ прошло · ❌ дефект · ➖ пропущено (недоступно в этом окружении).

---

## 0. Подготовка окружения

### Вариант A — локальный стек (без Telegram и блокчейна)

Проверяет всё, кроме подписи кошельком и реальных транзакций.

```bash
cd <репозиторий>
cp backend/.env.example backend/.env
```

В `backend/.env` для локального прогона:

```ini
ENV=dev
TELEGRAM_BOT_TOKEN=123456:LOCAL-TEST-BOT-TOKEN   # любой, подпись initData считается им же
ADMIN_TELEGRAM_IDS=777000
TREASURY_ADDRESS=0:1111111111111111111111111111111111111111111111111111111111111111
TON_VERIFY_MODE=mock      # платежи не проверяются в сети
SUBDOM_MODE=fake          # доменный сервис — заглушка
TON_STORAGE_MODE=local    # публикация в локальный каталог
```

```bash
printf 'POSTGRES_USER=ton\nPOSTGRES_PASSWORD=ton\nPOSTGRES_DB=ton_builder\n' > .env
mkdir -p nginx/certs
openssl req -x509 -nodes -newkey rsa:2048 -days 365 \
  -keyout nginx/certs/privkey.pem -out nginx/certs/fullchain.pem -subj "/CN=localhost"
cd frontend && npm ci && npm run build && cd ..
docker compose up -d --build postgres redis migrate backend worker scheduler nginx
```

Бот в этом варианте не поднимается: с ненастоящим токеном он уходит в
рестарт-цикл. Уведомления при этом не приходят — это ожидаемо.

Проверка готовности:

```bash
docker compose ps                 # backend/postgres/redis — healthy
curl -k https://localhost/health  # {"status":"ok",...}
docker compose logs migrate       # tariffs created: 5
```

Mini App открывается на `https://localhost` (сертификат самоподписанный —
браузер спросит подтверждение). Вне Telegram приложение само переключается на
встроенный мок контракта, поэтому UI работает целиком.

### Вариант B — боевой прогон

По [DEPLOY.md](DEPLOY.md): реальный домен с https, боевой токен бота,
`TON_VERIFY_MODE=onchain`, `SUBDOM_MODE=http`, `TON_STORAGE_MODE=daemon`,
кошелёк с TON на балансе. Только этот вариант проверяет оплату и домены по-настоящему.

### Вариант C — только интерфейс

```bash
cd frontend && npm install && npm run dev     # http://localhost:5173
```

Мок API включается сам. Данные лежат в localStorage, сбрасываются кнопкой
«Сбросить демо-данные» в профиле.

## Что уже проверено автоматически

Повторять руками не нужно — эти сценарии гоняются в тестах:

```bash
cd backend && pytest -q          # 41 тест: авторизация, лимиты, оплата, публикация, планировщик, админка
cd frontend && npm test          # 17 тестов: рендер, экранирование, sandbox, логика конструктора
python scripts/smoke_test.py     # 63 проверки по поднятому стеку (нужен запущенный docker compose)
```

`smoke_test.py` бьёт по живому API через nginx: миграции на Postgres, очередь
Redis, воркер публикации, админка и аудит. Каждый запуск заводит нового
пользователя, поэтому его можно гонять после каждого деплоя.

Сквозной прогон по живому стеку (63 проверки: auth → сайт → оплата → публикация
воркером через Redis → админка → аудит) выполнен на этом окружении и прошёл
полностью. Проверено вживую: миграции на Postgres, сид тарифов, публикация файла
в общий том, снятие сайтов планировщиком, отдача Mini App через nginx.

## Известные ограничения окружения

* **Оплата и домены в мок-режиме не проверяются по-настоящему.** `TON_VERIFY_MODE=mock`
  принимает любой хэш, `SUBDOM_MODE=fake` подставляет фиктивные адреса. Разделы 6–8
  имеют смысл только в боевом варианте B.
* **Уведомления требуют настоящего бота.** С тестовым токеном Telegram отвечает
  `Unauthorized`, backend это логирует и продолжает работу.
* **Пользователь должен нажать `/start`** — Telegram запрещает боту писать первым.
* **TON Storage.** При `TON_STORAGE_MODE=local` сайт рендерится в каталог, но не
  раздаётся сетью TON. Проверка домена в TON-браузере (9.8) возможна только с
  `storage-daemon`.
