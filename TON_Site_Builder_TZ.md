# TON Site Builder — Техническое задание для разработки

Telegram Mini App для создания и публикации мини-сайтов на доменах/субдоменах сети TON, с оплатой через TON Connect, системой подписок и админкой.

Документ разбит на две параллельные роли: **Разработчик A (Backend/Blockchain)** и **Разработчик B (Frontend/Mini App)**. Роли связаны единым **API-контрактом** (раздел 4) — это позволяет работать независимо: B пишет интерфейс против замоканного API, A реализует реальную логику под тот же контракт.

---

## 1. Общая архитектура

```
┌─────────────────────────────┐
│  Telegram Mini App (React)  │  ← Разработчик B
│  конструктор, шаблоны, UI,  │
│  админка, TON Connect UI    │
└──────────────┬──────────────┘
               │ REST API (раздел 4)
┌──────────────┴──────────────┐
│  Backend (FastAPI, Python)  │  ← Разработчик A
│  бизнес-логика, БД, оплата, │
│  подписки, публикация, бот  │
└───┬─────────────┬───────────┘
    │             │
    ▼             ▼
┌────────┐   ┌──────────────────┐
│subdom  │   │  TON Storage     │
│API     │   │  (публикация     │
│(блокч.)│   │   контента сайта)│
└────────┘   └──────────────────┘
```

**Принцип изоляции внешнего API:** вся работа с `subdom.zone` инкапсулируется в один модуль (`subdom_client`). Если сервис изменится или появится альтернатива — правится только этот модуль, остальная система не затрагивается. Это архитектурное требование, а не пожелание.

**Что хранится у нас (не у стороннего сервиса):** пользователи, подписки, тарифы, данные сайтов (структура блоков), метаданные публикаций. Даже при недоступности subdom API данные не теряются — временно недоступна только операция создания новых доменов.

## 2. Технологический стек

**Backend (Разработчик A):**
- Python 3.11+, FastAPI (async)
- PostgreSQL (основная БД)
- Redis (фоновые задачи, планировщик подписок, кэш)
- aiogram 3.x (Telegram-бот для уведомлений)
- pytoniq / TON SDK (проверка транзакций on-chain, работа с TON Storage)
- Docker + docker-compose

**Frontend (Разработчик B):**
- React 18 + TypeScript
- Telegram Web App SDK (`@twa-dev/sdk`)
- TON Connect UI (`@tonconnect/ui-react`)
- State management: Zustand или Redux Toolkit
- i18n: `i18next` (RU/EN)
- CSS: Tailwind или CSS-modules (по решению B), поддержка тёмной/светлой темы

**Согласовать между A и B до старта:**
- Точная структура JSON каждого типа шаблона (раздел 6)
- Формат ошибок API (единый)
- Схему авторизации (Telegram initData + TON Connect)

## 4. API-контракт (граница между A и B)

**Это самый важный раздел для параллельной работы.** B разрабатывает интерфейс, обращаясь к этим эндпоинтам (сначала к моку, потом к реальному backend от A). A реализует ровно эти эндпоинты. Согласуется и фиксируется в первый день, дальше меняется только по обоюдному согласию.

### Авторизация
Все запросы содержат заголовок `X-Telegram-Init-Data` (initData из Telegram Web App). Backend валидирует подпись initData. Для admin-эндпоинтов дополнительно проверяется `is_admin`.

### Пользователь и кошелёк
```
POST /api/user/auth
  body: { init_data }
  → { user: {...}, is_admin }

POST /api/user/connect-wallet
  body: { wallet_address, ton_proof }   # проверка владения кошельком
  → { success, wallet_address }

PATCH /api/user/settings
  body: { language?, theme? }
  → { success }
```

### Сайты (конструктор)
```
GET  /api/sites
  → [ { id, type, title, domain, status, ... } ]

POST /api/sites
  body: { type, title, content_json }
  → { site: {...} }

GET  /api/sites/{id}
  → { site: {...} }

PATCH /api/sites/{id}
  body: { title?, content_json?, custom_code? }
  → { site: {...} }

DELETE /api/sites/{id}
  → { success }

POST /api/sites/{id}/preview
  # генерирует HTML-превью из content_json, не публикуя
  → { preview_html }   # или preview_url во временном хранилище
```

### Домены и публикация (обёртка над subdom API + TON Storage)
```
GET  /api/domains/check?name=example&tld=ton
  # проверка доступности/статуса домена
  → { available, status, dns_item_address? }

POST /api/domains/deploy-zone
  # инициирует деплой зоны — backend дёргает subdom API,
  # возвращает готовую транзакцию для подписи в TON Connect
  body: { site_id, domain, tld, mode: "proxy"|"sbt" }
  → { transaction: { validUntil, messages: [...] } }

POST /api/domains/confirm
  # frontend сообщает, что транзакция подписана и отправлена
  body: { site_id, tx_hash }
  → { status: "publishing" }

POST /api/sites/{id}/publish
  # запускает публикацию контента в TON Storage
  → { status: "publishing", job_id }

GET  /api/sites/{id}/publish-status
  → { status, storage_bag_id?, error? }
```

### Подписки и тарифы
```
GET  /api/tariffs
  # активные тарифы для витрины
  → [ { id, name, sites_limit, duration, price_ton, kind } ]

POST /api/subscriptions/purchase
  # инициирует оплату подписки — возвращает транзакцию для TON Connect
  body: { tariff_id, site_id? }
  → { transaction: {...}, payment_id }

POST /api/subscriptions/confirm
  body: { payment_id, tx_hash }
  → { subscription: {...} }

GET  /api/subscriptions
  # подписки текущего пользователя
  → [ { id, tariff, expires_at, status, ... } ]
```

### Премиум-блок «Свой код»
```
POST /api/sites/{id}/custom-code/purchase
  → { transaction: {...}, payment_id }

POST /api/sites/{id}/custom-code
  # после оплаты — загрузка кода
  body: { html, css, js }
  → { success }
```

### Админка
```
GET   /api/admin/users?search=&page=
  → { users: [...], total }

GET   /api/admin/users/{id}
  → { user, sites, subscriptions, payments }

POST  /api/admin/users/{id}/grant-access
  body: { tariff_id, duration }
  → { subscription }

POST  /api/admin/users/{id}/revoke-access
  body: { subscription_id }
  → { success }

GET   /api/admin/tariffs
POST  /api/admin/tariffs        # создать
PATCH /api/admin/tariffs/{id}   # изменить цену/лимиты/активность
DELETE /api/admin/tariffs/{id}

GET   /api/admin/domains
  → [ { domain, user, site, status } ]

GET   /api/admin/stats
  → { total_users, total_sites, active_subscriptions, revenue }
```

### Единый формат ошибки
```json
{ "error": { "code": "STRING_CODE", "message": "human readable" } }
```

## 5. РАЗРАБОТЧИК A — Backend / Blockchain

Отвечает за сервер, базу данных, всю блокчейн-интеграцию, оплату, подписки, публикацию и бота. Ниже — задачи по блокам с деталями.

### A1. Каркас проекта и БД (2-3 дня)
- Инициализация FastAPI-проекта, структура папок, конфиг через `.env` (чёткое разделение тестовых/боевых значений — токены, адреса, ключи)
- Поднять PostgreSQL + Redis в docker-compose
- Реализовать все модели данных из раздела 3 (SQLAlchemy + Alembic-миграции)
- Middleware валидации Telegram `initData` (проверка подписи по bot token)
- Базовые эндпоинты `/api/user/auth`, `/api/user/settings`

### A2. Модуль subdom_client — изоляция внешнего API (2-3 дня)
**Критически важный модуль.** Вся работа с `subdom.zone` только здесь, наружу — свой чистый интерфейс.
- Обёртки над эндпоинтами subdom API:
  - `deploy_proxy_zone(dns_item_address, dns_item_name, user_wallet, tld)` → TransactionResponse
  - `deploy_sbt_zone(dns_item_address, domain, user_wallet, tld)` → TransactionResponse
  - `start_auction(collection_address, subdomain_name)` → TransactionResponse
  - `mint_sbt_subdomain(collection_address, subdomain_name)` → TransactionResponse
  - `claim_subdomain(subdomain_item_address)` → TransactionResponse
- Обработка ошибок subdom API, ретраи при временных сбоях, таймауты
- Проброс `TransactionResponse` (validUntil + messages) наверх без изменений — фронт передаст его в TON Connect
- **Абстракция:** интерфейс модуля не должен «протекать» деталями subdom наружу, чтобы замена сервиса не ломала остальной код

### A3. TON Connect backend — проверка оплаты on-chain (2-3 дня)
- Проверка `ton_proof` при подключении кошелька (подтверждение владения адресом)
- **Проверка фактического прохождения транзакций:** после того как фронт сообщает `tx_hash`, backend проверяет в блокчейне TON, что транзакция реально прошла, на нужный адрес и нужную сумму — только тогда активирует подписку/публикацию. Не доверять фронту на слово.
- Модуль работы с TON через pytoniq/TON API (получение статуса транзакции по хэшу)

### A4. Публикация в TON Storage (3-4 дня) ⚠️ зона неопределённости
- Генерация статического HTML/CSS/JS из `content_json` сайта (рендер по шаблону)
- Заливка готового сайта в TON Storage (создание «мешка» данных), получение `storage_bag_id`
- Привязка опубликованного контента к домену через DNS-резолвер
- Фоновая задача публикации (Redis queue) со статусами: publishing → published / publish_error
- **Примечание:** это самая рискованная часть. subdom API покрывает операции с доменами, но публикацию контента в Storage, вероятно, придётся реализовывать своим storage-daemon. На старте проекта выделить полдня-день на проверку реализуемости именно этого шага и согласовать подход.

### A5. Подписки и тарифы — бизнес-логика (3-4 дня)
- CRUD тарифов (для админки)
- Логика покупки подписки: создать Payment (pending) → вернуть транзакцию → после confirm проверить on-chain → активировать Subscription
- Лимиты: базовый тариф = 1 сайт, PRO = 5 / 25 сайтов; проверка лимита при создании сайта
- Логика сроков: month / 3 / 6 / 12 / forever; расчёт `expires_at`
- Бесплатная публикация первого сайта на 7 дней (автоматическая подписка типа trial)
- Планировщик (Redis + периодическая задача): перевод подписок в `expiring_soon` (за N дней) и `expired`, снятие сайта с публикации по истечении

### A6. Telegram-бот уведомлений (1.5-2 дня)
- aiogram-бот, отправка уведомлений пользователю по его telegram_id:
  - сайт опубликован
  - ошибка публикации
  - подписка заканчивается (за N дней)
  - подписка закончилась
- Триггеры уведомлений завязаны на события в системе (публикация, планировщик подписок)

### A7. Админ-API (3-4 дня)
- Все эндпоинты `/api/admin/*` из раздела 4
- Проверка прав (`is_admin`) на каждом admin-эндпоинте
- Ручная выдача/отзыв доступа (создание Subscription с `granted_by_admin=true`)
- Изменение цен/лимитов тарифов
- Статистика (пользователи, сайты, активные подписки, оборот)
- Аудит действий админа (AdminAction)

### A8. Деплой, документация, тесты (совместно с B в конце, ~2-3 дня)
- docker-compose со всеми сервисами (backend, PostgreSQL, Redis, бот, storage-daemon, nginx)
- Подробная инструкция по развёртыванию на чистом сервере (пошагово: установка Docker, клонирование, заполнение `.env`, запуск, проверка)
- Шаблон `.env` с чётким разделением тестовых/боевых значений
- Интеграционные тесты полного цикла: создание сайта → оплата → деплой домена → публикация → уведомление

## 6. РАЗРАБОТЧИК B — Frontend / Mini App

Отвечает за весь интерфейс Mini App, конструктор сайтов, шаблоны, предпросмотр, оплату (UI), админку. Работает против API-контракта (раздел 4) — до готовности backend использует мок-сервер с теми же эндпоинтами.

### B1. Каркас Mini App (2-3 дня)
- Инициализация React + TypeScript проекта
- Интеграция Telegram Web App SDK: initData, тема Telegram, кнопки, haptic feedback
- Интеграция TON Connect UI: подключение кошелька, отправка транзакций на подпись
- Роутинг (список сайтов / конструктор / подписки / админка)
- Светлая и тёмная темы (переключение + синхронизация с настройкой пользователя)
- i18n RU/EN (i18next), переключатель языка
- Слой API-клиента (обёртки над эндпоинтами раздела 4, единая обработка ошибок)

### B2. Конструктор сайтов — ядро (4-6 дней)
**Самая трудоёмкая часть фронта.** Гибкий редактор блоков.
- Механизм добавления/удаления/перемещения блоков
- Гибкие блоки: пользователь может добавлять произвольное число ссылок, кнопок, секций, картинок
- Загрузка изображений (в пределах ограничений)
- Редактирование текстовых полей, цветов, выбор фона сайта (пара вариантов фонов на выбор с предпросмотром)
- Сохранение структуры в `content_json` (формат согласуется с A)
- Автосохранение черновика

### B3. Шесть типов шаблонов (3-4 дня)
Каждый со своей структурой полей. Структуру `content_json` каждого типа согласовать с A в первый день.
- **Визитка:** имя/бренд, описание, кнопки связи, соцсети, фото
- **Ссылки (links page):** крупное фото/обложка, список ссылок, контакты
- **Лендинг:** обложка, преимущества, CTA, блок товара/услуги
- **Портфолио:** работы (галерея), описание, контакты, фото
- **События:** афиша, дата, место, программа, регистрация, фото
- **TON-проект:** тикер, адрес контракта, ссылки, jetton, описание проекта

### B4. Премиум-блок «Свой код» (1.5-2 дня)
- UI загрузки HTML/CSS/JS (только после оплаты — состояние блокируется до подтверждения)
- Редактор кода (подсветка синтаксиса, напр. CodeMirror)
- Предупреждение/превью пользовательского кода
- Инициация оплаты этого блока через TON Connect (цена приходит из админки)

### B5. Предпросмотр сайта (1.5-2 дня)
- Кнопка «Предпросмотр» до публикации
- Рендер сайта как он будет выглядеть (запрос к `/api/sites/{id}/preview` или клиентский рендер по `content_json`)
- Предпросмотр в мобильном и десктопном виде

### B6. Флоу публикации и оплаты (UI) (3-4 дня)
- Экран выбора/привязки домена (проверка доступности через API)
- Флоу деплоя зоны: запрос транзакции с backend → передача в TON Connect на подпись → отправка `tx_hash` на подтверждение
- Экран публикации со статусами (publishing → published / error), поллинг статуса
- Витрина тарифов (из `/api/tariffs`), выбор подписки
- Флоу оплаты подписки через TON Connect (аналогично деплою)
- Экран «Мои подписки» (сроки, статусы, продление)
- Уведомление о необходимости продлить (по истечении trial 7 дней)

### B7. Админ-панель (UI) (4-5 дней)
- Отдельный раздел, доступен только при `is_admin`
- Список пользователей (поиск, пагинация), карточка пользователя (сайты, подписки, платежи)
- Ручная выдача/отзыв доступа
- Управление тарифами: создание, изменение цены/лимитов/активности, удаление
- Список доменов
- Дашборд статистики (пользователи, сайты, активные подписки, оборот)

### B8. Финальная сборка, тесты, деплой (совместно с A, ~2-3 дня)
- Сборка Mini App, интеграция с реальным backend
- Прогон полного пользовательского сценария на реальных данных
- Проверка адаптива, тем, языков
- Участие в подготовке инструкции по деплою (фронтовая часть)

## 7. План параллельной работы (координация)

**День 1 (совместно, критично):**
- Зафиксировать API-контракт (раздел 4)
- Согласовать модель данных (раздел 3)
- Согласовать точную структуру `content_json` каждого из 6 шаблонов
- A поднимает мок-сервер эндпоинтов (или отдаёт OpenAPI-схему), чтобы B сразу работал против контракта

**Дни 2+ (параллельно):**
- A идёт по A1→A7, B идёт по B1→B7
- Точка синхронизации в середине: A выдаёт реальные эндпоинты по мере готовности, B переключается с мока на реальные
- **Ранний приоритет для A:** проверка публикации в TON Storage (A4) — это зона неопределённости, лучше снять риск в начале

**Финал (совместно):**
- A8 + B8: интеграция, сквозное тестирование, деплой, документация

**Разделение зон ответственности не пересекается:**
- A не трогает UI, B не трогает блокчейн/сервер
- Единственная общая точка — API-контракт, который зафиксирован в первый день

## 8. Важные технические заметки

- **Изоляция subdom API** — обязательна (модуль `subdom_client`). При смене/отключении сервиса правится только он.
- **Проверка оплаты только on-chain** — backend не активирует подписку/публикацию по слову фронта, а проверяет транзакцию в блокчейне по хэшу.
- **Данные — у нас** — пользователи, сайты, подписки хранятся в нашей БД, не у стороннего сервиса.
- **TON Storage (A4)** — единственная реально неопределённая часть, снять риск в начале отдельной проверкой.
- **`.env` с разделением тестовых/боевых значений** — чтобы перенос на боевой сервер сводился к замене файла, а не правкам в коде.
- **Безопасность пользовательского кода** («Свой код») — изолировать, не допускать выполнения произвольного JS в контексте платформы.
